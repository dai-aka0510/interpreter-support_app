# 卒制企画概要

## 1. サービス概要
フリーランスの通訳・翻訳者が、見積・請求・領収書整理などの「月末の経理・請求雑務」に追われる時間を最小化し、**収益に直結する本業の通訳・翻訳業務だけに全集中できるようにする「通訳者特化型 業務・経理効率化プラットフォーム」**です。

---

## 2. このアイデアはどこから生まれたか
### 2-1. きっかけとなった体験・感情
義母がプロのフリーランス通訳・翻訳者として活動する中で、月末になると見積書・請求書の作成やPCファイルでの書類管理作業に追われている姿を間近で見てきたこと。特に通訳案件に付随する領収書の整理や「これは経費になるのか？」「どの勘定科目なのか？」と悩みながら時間を取られている様子に強い違和感を抱いた。

### 2-2. なぜそれが「気になった」のか
義母は本来、高度な通訳・翻訳スキルで価値を生み出すプロフェッショナルであるにもかかわらず、月末になると「収益を生まない事務処理」に忙殺され、精神的にも疲弊していたから。家族として「会計の専門知識がなくても、本業だけに集中できる環境を作ってあげたい」と強く感じた。

---

## 3. 課題の整理
### 3-1. 表に見えている困りごと
- 月末に請求書・見積書作成作業が一気に集中する。
- 領収書のまとめやPC内でのファイル管理（見積・請求書）が煩雑。
- 経費になるかどうかの判断や、勘定科目が分からず調べる時間が無駄になっている。

### 3-2. 本当に解決したい課題は何か
- なぜ困るのか？ ➔ 月末に事務作業が集中し、本業の通訳準備や休息の時間が削られるから。
- なぜ？ ➔ 領収書の整理や管理が手作業で、勘定科目の判断にも迷うから。
- なぜ？ ➔ 一般の会計ソフトは機能が多すぎて難しく、通訳者の日常の動きに最適化されていないから。
- **本当に解決したい課題：** フリーランス通訳者が「会計知識の不安や月末の事務作業」に脳のメモリ（思考力）を奪われ、本来出すべきパフォーマンスを発揮できなくなっていること。

---

## 4. 想定ユーザーについて
### 4-1. 想定しているユーザー
- **ターゲット：** 50代後半～60代前半のフリーランス通訳・翻訳者（義母）
- **年齢：** 50代後半～60代前半
  - **理由：** ターゲットを「50代後半～60代前半・IT不得意・通訳者」という最もハードルの高い1人に特化して絞り込むことで、極限までシンプルな操作性と通訳特有の業務フローに最適化するため。（※まずは義母が100%使えるアプリとして完成させ、将来的に他のフリーランス全般へ横展開することを想定）
- **生活・状況：** 普段は自宅での通訳・翻訳や現場での通訳に追われ、月末にまとめて手帳や領収書を見ながらPCで請求書を作成している。
  - **理由：** 日常の中でスマホから領収書を撮影・記録しておくだけで、月末の作業がほぼ完了する仕組みが一番効果的だから。
- **環境：** 確定申告自体は税理士（JDL会計ソフト使用）に依頼している環境。
  - **理由：** アプリ側で複雑な確定申告書を作る必要はなく、「税理士（JDL）に渡す・入力するためのデータ整理（領収書画像・日付・金額・科目メモ）」と請求書発行に特化できるため。

### 4-2. 自分とユーザーの距離
- **選んだもの：** 身近な誰か（義母）
- **理由：** 実際に目の前でPCファイルや領収書と格闘しているリアルな現場を見ており、ヒアリングやテスト利用（フィードバック）をダイレクトに行えるため。

### 4-3. 実際に使われる可能性について
- **最初に使う人：** 義母
- **思い出す場面：** 領収書をもらった瞬間、見積・請求書を発行するとき、月末の経理整理のとき。
- **代わりに使っているもの：** PCのフォルダ管理、紙の領収書束、手書きのメモ。
- **置き換えて使う理由：** 写真を撮るだけで領収書とデータの整理が溜まり、迷いやすい「勘定科目」もガイド付きで一瞬で分類でき、ワンクリックで請求書PDF発行とJDL用CSV出力ができるから。

### 4-4. 導入・継続の流れ
- **きっかけ：** 月末に「また請求書作成と領収書整理で夜遅くなった」「これ何の経費だっけ？」と悩んだ瞬間。
- **最初の一歩：** アプリにログインし、スマホで領収書を撮影・保存してみる。
- **使い続ける理由：** 溜まったデータからボタン一つで「請求書PDF発行」と「税理士提出用CSV出力」が完了し、月末の事務作業が圧倒的にラクになる体験が得られるから。

## 5. 既存サービス・競合調査
### 5-1. 似たサービスの調査
- **サービス名：** TOKIUM / freee / 弥生会計
- **URL：** https://www.tokium.jp/
- **できること：** 領収書のスキャン・データ化、確定申告書類の作成、本格的な複式簿記管理。

### 5-2. それでも自分が作りたい理由
既存の会計ソフトは機能が多すぎて「青色申告の知識」がないと操作に迷う。ヒアリングの結果、義母のように「確定申告や出納帳管理は税理士（JDL）に任せている」人にとっては過剰機能であり、「日常の領収書撮影・JDL用データ整理・請求書発行」だけに特化したシンプルなツールが存在しないから。

### 5-3. 差別化を「体験価値」で表現する
- **差別化ポイント：** 「専門知識ゼロでも、**領収書を撮影してガイド通りに選ぶだけでデータが整い、月末の請求書発行と税理士用データの出力がわずか15分で終わる安心感**を提供する」

---

## 6. このサービスで提供したい価値
### 6-1. ユーザーの変化
- **行動の変化：** 月末にまとめて書類やPCファイルと格闘するのではなく、隙間時間に写真撮影と入力をしておくだけで、月末の請求書出力・CSV準備がすぐに終わるようになる。
- **気持ちの変化：** 「どの勘定科目で処理すべきか」「月末の請求書作成が面倒」という不安・ストレスが消える。
- **考え方の変化：** 「事務作業は大変なもの」から「ツールに任せて本業の通訳準備に全集中する」という意識へ変わる。

### 6-2. 価値を一文で表す
「このサービスは、月末の経理や書類管理に悩むフリーランス通訳者が、写真撮影と直感的な操作だけで事務作業を終わらせ、本業の通訳業務に全集中できるようになるサービス」

## 7. このアプリで実現すること
### MVPで作る機能（最小限の核となる機能）
1. **ユーザー認証機能**（ログイン・ログアウト）
2. **案件・タスク管理機能**（通訳案件の登録、見積書・請求書ステータス管理）
3. **領収書保存・明細管理機能**（スマホで領収書を撮影・保存し、日付・金額・勘定科目を案件に紐付けてメモ）
4. **JDL入力用 勘定科目アシスト表示**（税理士に渡す際に迷わないよう、通訳者がよく使う科目をガイド表示）
5. **請求書・見積書のPDF自動発行機能**（案件データからワンクリックで綺麗なPDFを出力）
6. **JDL提出用データ（CSV）の一括ダウンロード機能**（集計された経費データをボタン一つでCSV出力）

### 本リリースで作る機能（将来的な追加機能）
- OCR（画像文字認識）による領収書日付・金額の自動読み取り
- 出張手配メモ・リンク管理機能（新幹線やホテルの予約状態チェックと直リンク）
- 通訳仲間への案件引き継ぎメモ作成機能（案件情報をコピペ・共有しやすいフォーマットで出力）

## 8. このアプリの懸念点とその対策
### 懸念点①
- **何が問題になりそうか：** 50代後半のユーザー（義母）が、画像のアップロードやデータの入力操作で迷ってしまう可能性。
- **なぜそう思うか：** 日頃から多機能なITツールの操作に苦手意識を持っているため。
- **対策：** 画面のボタンを大きくし、1画面あたりの情報量を極限まで減らす。また「次にやるべきこと」を画面上にわかりやすく大きな文字で誘導するUI設計（TypeScript活用）にする。

---

## 9. 今後の展開・発展の方向性
### 今考えている発展案
- **機能追加の方向性：** 案件ごとの「通訳用・専門用語集メモ」も紐付けられるようにし、経理だけでなく通訳の「事前準備」も一元化できるようにする。
- **UI・体験の改善：** スマホ撮影からワンタップで保存・分類まで完了するショートカット機能の実装。

## 10. 技術スタック（手段としての技術）
### 10-1. 使用予定の技術
- **デザイン・UI設計：** Figma
- **フロントエンド：** HTML5 / CSS3 / JavaScript / TypeScript / Tailwind CSS
- **バックエンド（フレームワーク）：** Ruby on Rails
- **データベース：** PostgreSQL
- **テスト・静的解析：** RSpec / RuboCop
- **画像保存（ストレージ）：** AWS S3 (Active Storage)
- **デプロイ先：** Render

### 10-2. 技術選定の比較検討
| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | データベース連携（案件管理・領収書管理）や画像保存、CSV/PDF出力の仕組みが迅速に構築できるため |
| TypeScript | 採用 | JavaScriptに型安全性をプラスし、入力フォームや画像プレビューのUIエラーを未然に防ぎ、滑らかな操作感を実現したいため |
| Tailwind CSS | 採用 | ITに苦手意識があるユーザー向けの「大きく押しやすいボタン」「シンプルな視認性」を効率よくデザイン・実装するため |
| Figma | 採用 | コードを書き始める前に画面設計（ワイヤーフレーム）を作成し、操作感のヒアリング・検証を行うため |
| RSpec | 採用 | 金額や日付といった大切な経理・案件データを扱うため、データ処理の正確性を自動テストで担保するため |
| React | 不採用（本リリースで検討） | まずはRails×TypeScriptのMVPで完成を優先するため |
